# 自动化增量管线部署指南

> 配套主课件 §7.3「cron 自动化编译管线」。本指南是一份**能照着做的部署 how-to**：在你已经搭好个人大脑、会查询、接了 MCP、做过维护的基础上，再往前走一步——让大脑**自己**把新数据吃进来。

---

## 一、这份指南讲什么、什么时候需要它

到目前为止，你的个人大脑是**手动喂养**的：你写了新笔记，跑一次 `gbrain import`，库就更新了。这套流程回答的都是**静态**问题——把一批 markdown 一次性编译进库，之后它就不再变化。

但真实的知识库不是静态的。今天有新会议记录，明天有新邮件往来，后天又冒出一批讨论。如果大脑只在建库那一刻吸收了一批数据，第二天它就开始过时。要让它一直有用，你需要一条**持续把新数据吸收进来**的机制——而且最好是无人值守的：在你睡觉时，它自己把今天的新内容编译进库、自动重连图谱、自检健康状态，等你早上来查的时候，昨天发生的事它已经知道了。

这就是**自动化增量管线**：把「多源数据进场 → 增量编译 → 定时调度 → 持续生长 → 端到端可查询」固化成一条无人值守的流水线。

**什么时候你需要它？**

- 你的知识源**持续在变**（笔记每天写、邮件每天来、issue 每天提），手动 import 已经跟不上。
- 你希望**早上一打开就能查到昨天的事**，而不是先想起来去手动同步。
- 你的数据**来自多个地方**，想用一个大脑统一检索。

如果你的库基本是一次性建好、偶尔手动更新，那你**还不需要**这份指南——直接用 `gbrain import` 足够了。自动化的价值只有在「持续、多源、需要无人值守」时才显现。

**读这份指南前，你应该已经会：**

- 编译 vs 解释的区别，会装 GBrain，懂「源真相 vs 编译产物」。
- 会用 `gbrain import` / `extract` / `query` 这套基本命令。
- 有一个可直连的 embedding Key（如 DashScope），会基本的 git 操作（`add` / `commit` / `diff`）。

下面按四个环节展开：**多源进场 → 增量编译 → 定时调度 → 健康巡检**，每步给命令和说明，最后做一次「关键踩坑」小结。

---

## 二、先理解全局：管线长什么样

一条完整的自动化管线，本质上是把你已经会的几个零件，串成一台能持续运转的机器：

```
  多个数据源 ──→ 一个 git 源仓库 ──→ 增量 sync ──→ embed ──→ self-wiring 建图 ──→ doctor 自检
  (笔记/邮件/会议)    (源真相)        (只编译变化页)  (回填向量)   (自动连边)        (健康巡检)
                                          ↑
                                    调度器定时触发
                                  (launchd / cron)
```

关键点有三个：

1. **源仓库是一个 git 仓库**。增量编译靠 git diff 检测「哪些文件变了」，所以源数据必须放在 git 里，每次写入后 commit。
2. **每一轮由调度器触发**。调度器（macOS 上用 launchd，Linux 上用 cron）每隔一段时间跑一遍整条流水线。
3. **每一轮都是闭环**。从写入到自检全程由一个脚本无人值守跑完，跑完之后新内容立即可检索。

下面逐环节展开。

---

## 三、环节 1：多源数据进场

### 3.1 准备一个专用大脑

自动化管线最好用一个**独立的、干净的**大脑，和你日常用的默认大脑隔离开，这样你能干净地观察它的增量生长，也不会污染日常库。GBrain 用 `GBRAIN_HOME` 环境变量做这种隔离——指向哪个路径，就操作哪个大脑：

```bash
# 用 GBRAIN_HOME 指定一个专用 brain 路径，与默认 ~/.gbrain 隔离
mkdir -p ~/.gbrain-pipeline
GBRAIN_HOME=~/.gbrain-pipeline gbrain reinit-pglite \
  --embedding-model dashscope:text-embedding-v3 \
  --embedding-dimensions 1024 --yes
```

这里有一个容易踩的坑：`gbrain init` 会自动检测环境里的 `OPENAI_API_KEY`，并**默认**用 OpenAI 的 1536 维 embedding，即使你没显式要求。如果你想用 DashScope 的 1024 维，必须像上面那样用 `reinit-pglite --embedding-model dashscope:text-embedding-v3 --embedding-dimensions 1024` **显式覆盖**，否则维度对不上、后续 embed 会出问题。

### 3.2 把多个数据源写成 markdown，放进 git 源仓库

「多源」是自动化管线的定义性特征——如果只有单一来源，它就退化成普通的一次性 import 了。

真实管线的数据来自多个互不相同的系统：讨论消息、往来邮件、会议记录。你需要为每一类来源写一个**连接器**：从真实 API（或导出文件）拉取数据，转成带 frontmatter 的 markdown，写进一个统一的 git 源仓库。

下面用「连接器各产出一批文档，再加一批实体存根页，最后建 git baseline」的流程示意：

```bash
# 各个连接器把对应来源的数据转成 markdown 写进源仓库的子目录
python3 your-source-A-connector.py --out SOURCE_REPO/source-a/  --count 40
python3 your-source-B-connector.py --out SOURCE_REPO/source-b/  --count 35
python3 your-source-C-connector.py --out SOURCE_REPO/source-c/  --count 25
python3 create-entity-stubs.py     --out SOURCE_REPO/             # 人物/公司等实体存根

# 建立 git baseline（增量 sync 的起点）
git init SOURCE_REPO
git -C SOURCE_REPO add .
git -C SOURCE_REPO commit -m "baseline: 多源文档 + [[目录/slug]] wikilinks"
```

这里有两个工业级细节：

- **连接器要留一个增量接口**。给脚本加一个 `--start-idx` 之类的参数，允许「从第 N 条开始追加」，这样后续做增量时不会重名、不会重复生成。
- **文档里必须含跨源实体**。同一个人名（如 `[[people/garry-tan]]`）、同一家公司（如 `[[companies/openai]]`）要出现在多个来源里。否则后面的自动建图（self-wiring）**无边可建**——大脑里有页，但页与页之间连不起来。

### 3.3 把 baseline 全量编译进库

源仓库建好后，先做一次全量编译，建立大脑的初始状态：

```bash
GBRAIN_HOME=~/.gbrain-pipeline gbrain import SOURCE_REPO --no-embed   # 编译所有页
GBRAIN_HOME=~/.gbrain-pipeline gbrain embed --stale                   # 回填 embedding
GBRAIN_HOME=~/.gbrain-pipeline gbrain extract all                     # self-wiring 建图
GBRAIN_HOME=~/.gbrain-pipeline gbrain doctor --json > doctor-baseline.json   # 健康基线
```

跑完后，你应该看到大脑里有了一批页、100% 都 embed 了、自动连出了一批 typed edges（带类型的边），doctor 报告一个健康分数。这就是「baseline」——之后所有的增量都在它之上累加。

### 3.4 工业陷阱：wikilink 必须带目录前缀

这是自动建图最容易犯的第一个坑，而且**它静默失败、不报错**。

如果连接器生成的是 `[[Garry Tan]]` 这种「光秃秃」的 wikilink，`gbrain extract` 会返回 **0 条边、且不报任何错**——图谱静默地建不出来，你以为成功了，其实什么都没连上。

根因是 GBrain 的链接正则**只匹配 `[[目录/slug]]` 格式**，而且目录必须在白名单（如 `people` / `companies` / `meetings` / `concepts`）里。`[[Garry Tan]]` 不在白名单，被静默忽略。

正确做法：

- 把所有 wikilink 写成带目录前缀的形式，如 `[[people/garry-tan]]`、`[[companies/openai]]`。
- 在源仓库里**创建对应的实体存根页**——wikilink 必须指向大脑中真实存在的页，否则连不上。

记住这条原则：**GBrain 是「显式声明 > 语义推断」的**，它不会聪明地猜「Garry Tan 就是 people/garry-tan」，你得明确告诉它。

## 四、环节 2：增量编译

### 4.1 为什么要增量：sync vs import 的数量级差异

`gbrain import` 是**全量**编译——每次都扫描全部文件，是 O(n) 的。在持续生长的场景里，文件越堆越多，每次全量重导的成本随数据量线性上升，很快就跟不上了。

`gbrain sync --repo` 是**增量**编译——它用 git diff 检测「哪些文件变了」，**只编译变化的那几页**。

差异有多大？举个直观的对比：当你只改了 3 个文件，

- **增量 sync** 只处理这 3 个变化页。
- **全量 import** 要重新扫描全部页（可能是几百、几千、几十万页）。

在小样本实测里，一次增量 sync 大约是**一秒级**，而对应的全量扫描随规模上升到**分钟量级**——重点不在某个精确数字，而在**量级关系**：增量比全量快**约一个数量级**，而且这个差距随数据规模放大。在十几万文件的真实大脑上，sync 每次只扫几个改动文件、import 每次要扫十几万文件，这才是增量真正不可替代的地方。

### 4.2 关键操作：追加 → commit → sync → embed

先核实一手 flag，不要凭记忆：

```bash
GBRAIN_HOME=~/.gbrain-pipeline gbrain sync --help
```

几个关键 flag 的语义：

| flag | 作用 |
|------|------|
| `--repo <路径>` | 指定 git 仓库路径（**增量的核心**） |
| `--full` | 强制全量重 sync（对照基准用） |
| `--no-embed` | 跳过 embedding 步骤 |
| `--watch --interval N` | 轮询模式（一种自带的简易定时） |
| `--json` | 结构化输出（写进日志后好用 jq 解析） |
| `--yes` | 非交互（**cron 脚本必用**，否则会卡在确认提示） |

`sync --help` 末尾还有一句重要提示：**「PGLite 是单写入的，大批量 sync 前先停掉 `gbrain serve`」**——这条约束在环节 3 的 cron 脚本里会用到。

实际的增量流程：连接器追加新文档 → git commit → 增量 sync → embed：

```bash
# 1. 连接器从上次的 start-idx 续写，避免重名
python3 your-source-A-connector.py --out SOURCE_REPO/source-a/ --start-idx 40 --count 1
git -C SOURCE_REPO add --all && git -C SOURCE_REPO commit -m "incremental: new docs"

# 2. 增量 sync：读 git diff，只编译变化页
GBRAIN_HOME=~/.gbrain-pipeline DASHSCOPE_API_KEY=<key> \
  gbrain sync --repo SOURCE_REPO --no-pull --retry-failed --yes

# 3. 链式必须：回填 embedding
GBRAIN_HOME=~/.gbrain-pipeline DASHSCOPE_API_KEY=<key> gbrain embed --stale

# 4. self-wiring：自动建图
GBRAIN_HOME=~/.gbrain-pipeline gbrain extract --stale
```

正常情况下，sync 会精确报告 `imported=1`（或你实际改动的页数），`skipped=N`、`errors=0`——它**只命中变化页**，没碰别的。

**`embed --stale` 是不能省的链式步骤。** 这是 GBrain 的一条红线：sync 进来的新 chunk 如果不回填 embedding，它对检索就是**不可见**的——库里有这页，但你查不到。即使在小数据量下 sync 阶段会内联完成 embedding（`embed --stale` 返回「0 stale」），cron 脚本里仍应链上它作为**幂等安全保障**（为什么，见环节 5）。

### 4.3 关键发现：第一次 sync 必然是全量扫描

这是理解增量 sync 必须跨过的一个认知坎，否则你会误以为「sync 根本不增量」。

`gbrain import` **不建立 git 书签**。所以在一个由 import 建好的库上**第一次**跑 `sync --repo`，它必然先做一次**全量扫描**，目的是建立一个 git checkpoint（书签），记下「我同步到哪个 commit 了」。

真正的 O(diff)（只看变化量）增量行为，发生在 checkpoint 建立之后的**第二次** sync 起。

这个过渡顺序是**正确的，不是 bug**：

```
import 建 baseline
   └─→ 第一次 sync：全量扫描，建立 git checkpoint（这一次不增量，正常）
          └─→ 第二次 sync 起：真 O(diff)，只扫变化页（这才是增量该有的样子）
```

机制对照如下：

| 指标 | 真 O(diff) sync（第 2 次起） | 全量 import |
|------|------|------|
| 检测机制 | git diff，O(diff 大小) | O(n) 文件全扫 |
| 实际扫描文件数 | 只扫变化页（如 3 个） | 全部页 |
| git 书签 | 有 checkpoint，下次继续 O(diff) | 无，下次仍 O(n) |

一个诚实的注脚：在小规模（百来个文件）下，第一次 sync 因为含 embedding 调用，反而可能比全量 import **更慢**。所以增量的价值**不在「第一次比全量快」**，而在**「建立 git 书签后，后续每次只扫变化量」**，并且要在大规模下才呈现数量级优势。别被「第一次没快」误导。

### 4.4 幂等性

再次 sync 时，若源仓库无变化，应返回「Already up to date」——这是一次 O(1) 的 git HEAD 比较，没有多余的 API 调用。这意味着你可以放心地让调度器**反复触发**，没有变化时它几乎零成本地立即返回。

## 五、环节 3：定时调度

「定时」是自动化管线的灵魂——**不真触发，它就只是一个手动脚本**。这一节是整份指南最有运维含金量的部分，也是踩坑最多的地方。

### 5.1 先写一个 cron 包装脚本

要让管线无人值守，需要把整条流水线串成一个 bash 脚本，让调度器去跑它。脚本骨架长这样：

```bash
#!/usr/bin/env bash
# 把环境变量显式 export —— cron/launchd 环境没有你 shell 里的上下文
export GBRAIN_HOME="$HOME/.gbrain-pipeline"
export DASHSCOPE_API_KEY="sk-你的key"     # cron 环境无 shell 上下文，须显式 export
export PATH="$HOME/.local/bin:/usr/local/bin:$PATH"   # 让脚本能找到 gbrain

# PGLite 是单写入的：写入前先停掉可能在跑的 serve，避免写锁冲突
pkill -f "gbrain serve" 2>/dev/null || true

SOURCE_REPO="$HOME/my-knowledge-repo"

# 1. 连接器写入新数据（你自己的拉取逻辑）
python3 "$HOME/connectors/run-all.py" --out "$SOURCE_REPO"

# 2. git commit（增量 sync 的锚点 —— 没 commit 的文件不会被 sync）
git -C "$SOURCE_REPO" add --all
git -C "$SOURCE_REPO" commit -m "cron cycle $(date +%s)" || true

# 3. 增量编译 → 回填 embedding → 自动建图
gbrain sync --repo "$SOURCE_REPO" --no-pull --retry-failed --yes
gbrain embed --stale          # 安全网，必须链上
gbrain extract --stale        # self-wiring

# 4. 健康巡检（结构化输出入日志）
gbrain doctor --json 2>/dev/null > "$HOME/.gbrain-pipeline-logs/doctor-$(date +%s).json"
```

脚本里有**三个工业级要点**，都来自你日常 shell 里不会遇到、但 cron 环境一定会遇到的运维经验：

1. **绝对路径 + 显式 export**。cron / launchd 环境**没有**你登录 shell 里的 PATH 和环境变量。所以 `gbrain` 最好用绝对路径（或在脚本里手动设 PATH），Key 和 `GBRAIN_HOME` 必须显式 `export`，否则脚本一跑就找不到命令、连不上 Key。
2. **PGLite 单写入保护**。PGLite 同一时刻只允许一个写入者，脚本开头必须 `pkill -f "gbrain serve"`，把可能常驻的查询服务停掉，否则 sync 会因写锁冲突失败。
3. **路径含空格要引号**。源仓库路径如果含空格，脚本里所有路径都要用引号包裹。

### 5.2 关键陷阱：macOS 不要用 crontab，要用 launchd

如果你在 macOS 上图省事，第一反应可能是用 crontab：

```bash
echo "*/2 * * * * /bin/bash cron-pipeline.sh >> cron.log 2>&1" | crontab -
```

**这在 macOS 上会失败。** 现象是脚本启动后立刻被杀，日志里看到 `EXIT:143`（也就是收到 SIGTERM 被强制终止）。根因是 macOS 上 crontab 是 setuid root 的，在非交互、非 TTY 的环境下会被系统直接 SIGTERM 掉。

**正确做法：改用 launchd 的 LaunchAgent。** 它是用户级的、不需要 root、加载时也不需要 TTY，完美适配无人值守场景。

创建一个 plist 文件：

```bash
cat > ~/Library/LaunchAgents/com.you.gbrain-pipeline.plist << 'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.you.gbrain-pipeline</string>
  <key>Program</key>
  <string>/bin/bash</string>
  <key>ProgramArguments</key>
  <array>
    <string>/bin/bash</string>
    <string>/Users/你的用户名/cron-pipeline.sh</string>
  </array>
  <!-- StartInterval：每隔多少秒触发一次 -->
  <key>StartInterval</key>
  <integer>120</integer>
  <key>RunAtLoad</key>
  <true/>
  <key>StandardOutPath</key>
  <string>/Users/你的用户名/.gbrain-pipeline-logs/stdout.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/你的用户名/.gbrain-pipeline-logs/stderr.log</string>
</dict>
</plist>
EOF

# 加载并验证
launchctl load ~/Library/LaunchAgents/com.you.gbrain-pipeline.plist   # 成功返回 EXIT:0
launchctl list com.you.gbrain-pipeline                                # 验证已加载
```

**关于 `StartInterval` 字段**：它是「每隔多少秒触发一次」。上面写的 `120`（2 分钟）只是**演示用**，方便你快速看到效果。**生产环境应该改成更长的周期**，比如 `900`（15 分钟）。不要在生产里用 120 秒，那会让管线过于频繁地空转。

`launchctl load` 返回 `EXIT:0` 且 `launchctl list` 能看到你的 Label，就说明调度器装好了，它会按 `StartInterval` 自动触发你的脚本。

### 5.3 关键陷阱：launchd 不能写 exFAT 可移动磁盘

这是一个隐蔽但致命的坑。

macOS 的 LaunchAgent 跑在一个有沙箱限制的会话里，**对可移动磁盘（如 exFAT 格式的外接 SSD / U 盘）没有写权限**。如果你把源仓库放在外接 exFAT 盘上，launchd 触发脚本时会报 `PermissionError: Operation not permitted`——调度器明明触发了（系统日志里能看到一次次时间戳），但每次写入都失败。

这条限制翻译成一句生产铁律：

> **源仓库必须放在本机 APFS 磁盘（`~/` 下），不能放在外接 exFAT SSD / U 盘上。**

这也是为什么前面建议把专用大脑建在 `~/.gbrain-pipeline`（本机 APFS）。把源仓库和大脑都放本机磁盘，这个坑就绕过去了。

### 5.4 跑几轮，看它持续生长

装好后，让它跑至少 3 轮（或手动 `bash cron-pipeline.sh` 触发几次），你应该看到大脑在每一轮稳定、单调地变大——页数每轮净增、图谱边数同步增长、每次增量 sync 都是一秒级。这条单调上升的曲线，就是「持续生长」的字面证据：每一轮内部，从写入到自检全程由脚本无人值守跑完。

### 5.5 关于 git commit 的锚点

特别强调一个容易忽略的点：**增量 sync 依赖 git commit 作为锚点**。`sync --repo` 是靠对比 git commit 来决定「哪些文件变了」的，所以：

> **没有 commit 的文件，不会被 sync。**

如果你的连接器写了文件却没 `git add && git commit`，那些文件对 sync 来说**根本不存在**。所以 cron 脚本里「写入 → commit → sync」这个顺序一步都不能少，commit 必须在 sync 之前。

## 六、环节 4：健康巡检

无人值守的管线**必须能自检**，否则它会**静默腐烂**——embed 失败、schema drift（结构漂移）都可能在没人盯着的时候悄悄发生。

### 6.1 把 doctor 写进 cron 日志

你已经会用 `gbrain doctor` 做交互式人工检查。在自动化管线里，把它升级为 `gbrain doctor --json`，每轮 cron 把结构化结果写进日志，之后可以用 jq 等工具机械解析：

```bash
gbrain doctor --json 2>/dev/null > doctor-cycle-$(date +%s).json
```

注意 `2>/dev/null`——把 stderr 的 phase 日志导走，确保输出是**纯 JSON**，否则 jq 解析会被污染。

### 6.2 关键发现：embed --stale 是幂等安全网

这是健康巡检最重要的价值，用一个真实场景说明。

假设某一轮 embedding 时，embedding 服务遇到一次瞬时网络故障（比如 SSL 抖动），导致 10 个 chunk 里有 7 个 embed 失败。如果管线就此放任，这 7 页对检索就**永久不可见**了——你以为它们进库了，其实查不到。

`gbrain embed --stale` 是一个**幂等重试机制**：它**只 embed 还没有 embedding 的 chunk**，可以反复调用，不会重复 embed 已经做完的。所以遇到上面那种故障，只要下一轮（或同一轮再链一次）`embed --stale`，那 7 个掉队的 chunk 会全部补回填，终态恢复到 100% 覆盖。

这就是为什么 cron 脚本里 sync 之后**必须**链 `embed --stale`：

- 即使 sync 阶段已经内联 embed 了（返回 0 stale），它作为安全网也**几乎零成本**。
- 而一旦遇到网络故障，它就是防止「库里有页查不到」的**最后一道防线**。

### 6.3 关键发现：低 health_score 是诊断，不是故障

你可能会看到 doctor 报告一个**偏低的 health_score**（比如标记为 unhealthy），初看像是大脑坏了。**先别慌**——读懂它需要区分两件事。

低分**不一定**意味着数据损坏。常见的两类扣分来源都是「正常的」：

1. **opt-in 功能未启用**。一些可选功能（如 nightly quality probe、conversation facts backfill）没配置，会被扣分——但你压根没打算用它们。
2. **schema coverage 不满**。比如某个连接器生成的 frontmatter 格式不匹配 GBrain 内置的某种 pattern，导致一部分页不被某个特性识别——但它们的 embedding 和检索完全正常。

**关键判断标准：看核心指标 `embeddings` 是不是 100% 覆盖。** 只要 embeddings 100%、0 stale，你的检索功能就是完全正常的。这种情况下，低 health_score 的正确读法是「**还有优化空间**」，而不是「**大脑损坏了**」。

doctor 在自动化管线里的真正价值是「**早发现 schema drift**」——当某一天分数突然掉下来、或 embeddings coverage 跌破 100%，那才是需要你介入的信号。生产里可以加一条阈值告警（如 embeddings coverage < 100% 时通知你），但告警接线本身属于运维工程，不在编译管线核心里。

## 七、诚实收口：set-and-forget 是神话

最后，回答一个你配完这条管线后最容易误判的问题：**「配好这条 cron 管线，是不是就一劳永逸了？」**

答案是**否定的**。这不是给技术泼冷水，而是给你一个诚实的决策框架。把三笔账摊开看：

| 成本项 | 量级 | 说明 |
|--------|------|------|
| **入库时（ingestion）token** | ≈ 0 | self-wiring 零 LLM 调用，增量编译只算 embedding，几乎不烧 LLM token。**这是编译式 RAG 的真实优势。** |
| **查询时（query）token** | 高（约一个数量级于普通向量 RAG） | 编译式 RAG 在查询时要把编译产物喂给 LLM 做跨源合成，token 反而更高。它换来的是**合成质量**，不是成本。 |
| **数据治理（curation）成本** | 高 | **最容易被忽略的一笔。** 那些不匹配 pattern 的页、wikilink 格式约定、schema 纪律，都是隐藏的**人力维护**。 |

把三笔账合起来看，结论很清楚：

> 低入库成本，是用**持续的人力维护**（schema 纪律、格式约定、健康巡检的跟进）换来的。
>
> 管线能无人值守地**运转**，但不能无人值守地**保持健康**。所谓 set-and-forget（配一次永久不管）是**神话**。

那个偏低的 health_score，就是这个张力的量化体现——它在提醒你「还有维护工作要做」。

所以，编译式自动化管线适合「**跨源合成质量优先、愿意付出维护纪律**」的场景；不适合「**只想省钱、不想维护**」的场景。想清楚这一点，再决定要不要为你的知识库配这条管线。

## 八、关键踩坑小结

把全程最容易栽跟头的坑集中列一遍，部署前对照检查：

| 踩坑 | 环节 | 教训 |
|------|------|------|
| wikilink 写成「光秃秃」的 `[[名字]]` | 多源进场 | 必须带目录前缀 `[[目录/slug]]`，否则**静默不建边且不报错**；显式声明 > 语义推断 |
| 以为第一次 sync 就该增量 | 增量编译 | import 不建 git 书签；**第一次 sync 必然全量扫描**建 checkpoint，第二次起才真增量 |
| sync 后忘了 `embed --stale` | 增量 / 健康 | 不回填 embedding 的新 chunk **对检索不可见**；它还是网络故障时的幂等安全网 |
| 文件没 commit 就指望被 sync | 定时调度 | 增量 sync 以 **git commit 为锚点**，没 commit 的文件不会被 sync |
| macOS 用 crontab | 定时调度 | crontab 在非 TTY 被 **SIGTERM（EXIT:143）杀掉**；改用 launchd LaunchAgent（用户级、无需 root） |
| 源仓库放外接 exFAT 盘 | 定时调度 | launchd 对可移动盘有沙箱限制（**Operation not permitted**）；源仓库必须放本机 APFS（`~/` 下） |
| cron 脚本没显式 export 环境 | 定时调度 | cron/launchd 无 shell 上下文；gbrain 用绝对路径、Key 与 `GBRAIN_HOME` 必须显式 export |
| 写入时没停 `gbrain serve` | 定时调度 | PGLite 单写入；脚本开头 `pkill -f "gbrain serve"` 防写锁冲突 |
| 演示用的 120 秒间隔直接上生产 | 定时调度 | `StartInterval` 演示用 120，生产改 900（15 分钟）或更长，避免频繁空转 |
| 看到低 health_score 就以为坏了 | 健康巡检 | 只要 **embeddings 100%** 检索就正常；低分多来自 opt-in 未启用 + schema coverage，是「优化空间」非「损坏」 |

## 九、迁移到你自己的数据

这条管线骨架（多源连接器 → git 源仓库 → 增量 sync → 调度器 → 持续生长 → 查询）和具体业务无关，可以整体迁移到任何「多源、持续更新、需检索」的知识库场景，比如个人笔记大脑、团队工程知识库、投研尽调大脑等。

迁移时改什么、不改什么：

| 改造点 | 改什么 | 不改什么 |
|------|------|------|
| 数据源连接器 | 把示例生成换成你的真实 API 拉取 → markdown | wikilink `[[目录/slug]]` 约定、`--start-idx` 增量接口 |
| 实体命名空间 | 设计你自己的目录白名单（people / projects / ...） | self-wiring 零 LLM 建图机制 |
| 调度周期 | `StartInterval` / cron 表达式改成生产周期 | 绝对路径、显式 export、PGLite 保护 |
| 查询探针 | 换成你领域的独特关键词与语义 query | `--no-expand` flag（验证检索时建议带上，走稳定的三路融合） |

最后给一份可直接套用的命令模板：

```bash
# 1. 建专用 brain（本机 APFS 路径，隔离）
GBRAIN_HOME=~/.gbrain-<你的场景> gbrain reinit-pglite \
  --embedding-model dashscope:text-embedding-v3 --embedding-dimensions 1024 --yes

# 2. 源仓库放本机 APFS（不放外接盘）+ git baseline
cd ~/my-knowledge-repo && git init && git add . && git commit -m "baseline"

# 3. cron 脚本核心（连接器 → commit → 增量 sync → embed 安全网 → 自检）
git -C ~/my-knowledge-repo add --all && git -C ~/my-knowledge-repo commit -m "cycle" || true
gbrain sync --repo ~/my-knowledge-repo --no-pull --yes
gbrain embed --stale
gbrain doctor --json 2>/dev/null > doctor-$(date +%s).json

# 4. 装 launchd（macOS），StartInterval 改成生产周期（如 900 = 15 分钟）
#    plist 模板见环节 5.2
launchctl load ~/Library/LaunchAgents/com.<你的标签>.plist
```

**验证管线闭环的最简方法**：写一篇含独特关键词的探针文档 → 跑一轮管线 → `gbrain query "独特关键词" --no-expand` 验证命中。把这条做成部署后的自动测试，每次都能确认管线没断。
