# 团队大脑部署指南：从个人 brain 到多人隔离的公司知识库

## 这份指南讲什么、什么时候需要它

你已经学会了用 GBrain 把个人 markdown 笔记编译成一个带向量索引、关系图谱、混合检索的本地知识大脑，也会查询、接 MCP、做日常维护。个人 brain 的形态是「单用户、单库、谁都全见」——你自己用，没有权限问题。

但当知识库要给一个团队共用时，会冒出三个个人 brain 从来不需要解决的工程问题：

1. **多人并发**：个人 brain 默认用的 PGLite（一个跑在进程内的嵌入式 Postgres）是单写者单进程引擎，本质是个人工具。多人同时连接、同时读写，必须换成能接受多连接的自托管 Postgres。
2. **多 source 切分**：一个库里要同时装下「全员可读的公共内容」「某个人的私有客户笔记」「绝不能外泄的敏感内部材料」三套独立命名空间。
3. **按权限隔离**：每个人用各自的凭证接入，数据库层强制只能读到被授权的内容——而且这个隔离必须可证、不可绕过。

这份指南就是教你把上面三件事从零跑通。设想一个典型场景：一个创业团队里有三个角色，各自攒了一堆笔记——

- **Alice**（销售）：客户页、会议纪要、续约跟进、合同金额。
- **Bob**（运维）：内部系统文档、值班记录，以及部分内部敏感材料。
- **Carol**（法务 / HR）：绩效复盘、薪酬调整、绩效改进计划、NDA、供应商合同。

三个人都想把笔记汇成**一个**共享的公司 brain，互相能查到对方沉淀的知识，避免信息孤岛。但有一条红线：**绩效、HR、法务这类敏感内容，绝不能泄漏到销售对客户问题的查询里**。Alice 查「客户最近的进展」时，结果里不该出现同事的绩效评分；Bob 排查内部问题时，则需要能读到这些内部页。

> **本指南最核心的一条认知**：在同一个知识库里做按人隔离的访问控制，**隔离必须落在数据库层、可机械核验、不依赖大模型的「配合」**。让大模型「自己别看敏感内容」是反模式——它有可能不听话，而且没法机械验证。正确做法是在 SQL 检索的那一层就强制 `source_id IN (该用户被授权的 source 集合)`，从根上让越权数据进不了结果。

下面按「环节」展开，每步给命令和说明，最后有一个关键认知 / 踩坑小结。本指南用的是程序化生成的拟真虚构数据（零隐私风险），你照着做时换成自己团队的真实语料即可。

## 环节一：准备多 source 公司语料 + 建库

### 1.1 用独立位置建公司 brain，不污染个人库

第一步是保护你已有的个人 brain。个人 brain 默认在 `~/.gbrain`。公司 brain 要用一个**独立的位置**，靠 `GBRAIN_HOME` 环境变量指向它，这样两个 brain 在同一台机器上物理隔离、互不污染——换工作场景不会动到你的个人知识库。

`GBRAIN_HOME` 是否真的切换了 brain 位置，可以这样自检：

```bash
GBRAIN_HOME=/tmp/test-brain gbrain stats
# 若返回 "No brain configured"，说明环境变量确实把 brain 位置切走了
```

后面所有公司 brain 的命令都要带上 `GBRAIN_HOME="<公司brain目录>"` 前缀。

### 1.2 准备三套 source 的语料

公司语料和个人语料的区别在于**规模和结构**：要跨多个 source、含真实的敏感靶子页、每页带结构化字段。这是隔离能不能验证的前提——没有真实的敏感内部页，「Alice 搜不到绩效」根本无从谈起。

按三套独立命名空间组织目录：

- `shared/`：公司 wiki、人物页、决策记录、政策、OKR，全员可读。
- `customers/alice-example/`：客户页（含会议、决策、跟进笔记），对应 Alice 的客户范围。这里的 `alice-example/` 是 per-person 子目录的写法，sync 后这些页都归属 customers source。
- `internal/`：`performance/` 绩效复盘、`hr/` HR 记录、`legal/` 法务合规——这些是隔离验证的**靶子**。其中至少要有一个明确的关键靶子页，比如 `internal/performance/performance-review-2025-h1.md`。

页与页之间用 `[[wikilink]]` 互链（人↔公司↔会议↔决策），为后续自动建图和跨页召回提供底座。一个工业规模的语料大致是 ≥100 页、跨 3 source、几百条 wikilink 这个量级。

### 1.3 建库与导入（含一个关键配置坑）

建库用 `gbrain init`，配 embedding 模型（这里用 DashScope 的 `text-embedding-v3`，1024 维）。然后导入全部语料：

```bash
GBRAIN_HOME="<公司brain目录>" gbrain init --pglite \
  --embedding-model dashscope:text-embedding-v3 \
  --embedding-dimensions 1024

GBRAIN_HOME="<公司brain目录>" gbrain import corpus/
```

> **关键配置坑（用 GBRAIN_HOME 跑多 brain 一定会撞）**：`gbrain config set provider_base_urls.dashscope ...` 这条命令会把配置写进**默认位置** `~/.gbrain/config.json`，**不会**写进 `GBRAIN_HOME` 指向的公司 brain 的 config。结果是第一次 import 时所有页 embedding 全部 auth fail（报 "Incorrect API key provided"），但同一个 key 直接 `curl` DashScope 又能成功——这就是多 brain 场景下 config 写入路径有歧义导致的。
>
> **解法**：用 `python3` 直接把 `provider_base_urls` 字段写进公司 brain 自己的 `config.json`，再重新 import。这是单 brain 场景遇不到的新坑。

导入完成后用 `gbrain stats` 和 `gbrain doctor` 核验。预期输出大致是：

```
# gbrain stats
Pages: 100   Chunks: 101   Embedded: 101   Tags: 84

# gbrain doctor（关键看这两项）
embed: 35/35 (101/101 全部嵌入)     ← 本环节核心验收指标，100% 嵌入
Overall health: 25/100              ← import-only brain 的正常基线，不必惊慌
```

`embed` 达到 100% 是本环节最重要的验收指标。Overall health 偏低（25/100）是新建的、只 import 没 wiring 的 brain 的正常基线——links / timeline 各项此时为 0，要等下个环节 sources wiring 后才上升。

### 1.4 迁 Postgres：为什么要迁、怎么迁

公司 brain 的「多人」本质需要能多连接的后端。**PGLite 是单进程引擎，一个进程独占一把写锁，天然不支持多并发用户**——它适合个人，不适合团队。所以生产部署要把库迁到本地 Docker 起的 Postgres（带 pgvector 向量扩展）。

装了 Docker 的完整迁移流程：

```bash
# 1. 起一个带 pgvector 的 Postgres 容器
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres pgvector/pgvector:pg16

# 2. 指向这个 Postgres
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/gbrain

# 3. 迁移
gbrain migrate --to supabase

# 4. 核验：迁移后 Postgres 的页数应当等于 PGLite 原值（迁移无损）
gbrain doctor
gbrain stats
```

> **关于 `migrate --to supabase` 这个命令名**：命令名里的 "supabase" 只是表示「用 PostgresEngine 这套后端」，连本地自托管的 Postgres 就行，**不需要任何云账号**。别被名字误导。

**如果你的机器没装 Docker / Postgres 工具链**，可以先这样核验环境：

```bash
which docker    # 是否装了 Docker
which podman    # 或 Podman
psql --version  # 是否有 psql 客户端
lsof -i :5432   # 5432 端口是否在监听
```

没有 Postgres 工具链时，可以**暂时留在 PGLite 上跑通后面所有隔离演示**——因为有个关键事实：

> **隔离机制与存储后端无关**。OAuth 权限隔离是 SQL 层的 `federated_read` 强制过滤，在 PGLite 和 Postgres 上**逻辑完全一致**。所以即使你暂时跑在 PGLite 上，环节二、三的隔离核心成果照样能完整演示和验证。Postgres 只是为了支撑真正的多人并发，不影响隔离逻辑本身。等你要上多人生产时，再补这一步迁移即可。

本环节产出：一个 ≥100 页、跨 3 source（含 ≥5 敏感 internal 页）的公司 brain，独立于个人 brain。规模过了工业门槛、敏感靶子就位，地基铺好。

## 环节二：切分 source + 起 OAuth 服务 + 注册 scoped 客户端

环节一的页此刻全在 default source 里。本环节要把它们切成三个 named source，起一个 HTTP MCP 服务，并为三个人各注册一个带读写权限边界的 OAuth 客户端。这是「个人工具」升级为「多用户基础设施」的关键一跃。

### 2.1 切分三个 named source

`gbrain sources add` 在 brain 里注册一个 named source，`--path` 指向对应的本地目录：

```bash
gbrain sources add shared    --path corpus/shared    --name "Shared company wiki"
gbrain sources add customers --path corpus/customers --name "Customer notes"
gbrain sources add internal  --path corpus/internal  --name "Internal-only"
```

> **隔离的基础默认值**：新建的 source 默认 `federated: false`（即默认隔离）。一个 source 只有在某个 OAuth 客户端的 `--federated-read` 里被**显式列出**时，才会被那个客户端搜索到。这个「默认不可读、显式才放行」的默认值，正是 leak-free 隔离的底层基础。

用 `gbrain sources list` 核验三个 source 就位（应能看到 default、shared、customers、internal 四个，各带 local_path）。

### 2.2 sync 各 source（两个静默坑）

把各 source 目录的内容同步进库并打上 source_id。这里有两个**不报错、但会让人困惑**的坑，必须按正确路径走：

```bash
# 正确路径：每个 corpus 子目录先 git init，再用 gbrain sync --source 同步
cd corpus/internal  && git init && git add . && git commit -m "internal corpus"
cd corpus/shared    && git init && git add . && git commit -m "shared corpus"
cd corpus/customers && git init && git add . && git commit -m "customers corpus"

gbrain sync --source internal  --no-pull
gbrain sync --source shared    --no-pull
gbrain sync --source customers --no-pull
```

> **两个静默坑（务必记住）**：
> 1. **`gbrain sync` 要求目标是 git 初始化的仓库**。对普通目录直接 sync 会报 "Not a git repository"。所以每个 corpus 子目录都要先 `git init` + commit。
> 2. **`gbrain import --source <id>` 会静默忽略 `--source` 参数**，页面全落到 default——命令不报错，但 source 路由实际失效了。**source 路由必须走 `gbrain sync`（它基于 git），不能用 `import --source`**。
>
> 这两个坑都不抛异常，只能靠下面的 `sources status` 核验页数分布才能发现。

sync 完用 `gbrain sources status` 看板核验。预期看到三个 source 各自非空、各带同步时间戳：

```
SOURCE      PAGES   LAG    EMBED    LAST_SYNC
shared      40      0s     100%     ...
customers   35      0s     100%     ...
internal    26      0s     100%     ...
```

三个 source 各有独立页数、互不串扰。这套结构是隔离的物理基础——没有 source 切分，就无从谈「谁能读哪些 source」。

### 2.3 起 HTTP MCP + OAuth 服务

`gbrain serve --http` 在本地起一个带 OAuth 2.1 的 HTTP MCP（模型上下文协议，Model Context Protocol）服务。本地 localhost 即可，不用开 `--bind 0.0.0.0`、也不用挂 ngrok——同一台机器上用不同凭证 hit `localhost:3131`，已经足够模拟多个 teammate 接入：

```bash
nohup env GBRAIN_HOME="<公司brain目录>" \
  gbrain serve --http --port 3131 > /tmp/gbrain-serve.log 2>&1 &
```

启动 banner 会打印出 **admin bootstrap token（务必存好）**，并显示当前状态。预期：

```
GBrain MCP Server v0.42.38.0
Port: 3131   Bind: 127.0.0.1   Engine: pglite
Issuer: http://localhost:3131
Clients: 0          ← 还没注册客户端
Admin Token: <存好这个>
```

核验服务活着：

```bash
curl localhost:3131/health
# 预期返回：{"status":"ok","version":"0.42.38.0","engine":"pglite"}
```

首次启动 `Clients: 0` 是正常的，OAuth 客户端还没注册。

### 2.4 注册三个 scoped OAuth 客户端（本环节灵魂）

这是整套方案的灵魂命令。每个人注册一个 `client_credentials` 类型的客户端：`--source` 定义**写权限**（单个 source），`--federated-read` 定义**读权限**（可以是多个 source）。

```bash
# 注意：PGLite 是单写者，serve 进程持有写锁。
# register-client 是写操作，serve 在跑时它会超时报 "Timed out waiting for PGLite lock"。
# 正确顺序：先停 serve → 注册全部客户端 → 再重启 serve
kill -TERM $(pgrep -f "gbrain serve")

gbrain auth register-client alice-example --grant-types client_credentials \
  --scopes "read write" --source customers --federated-read customers,shared
gbrain auth register-client bob-example   --grant-types client_credentials \
  --scopes "read write" --source internal  --federated-read internal,shared
gbrain auth register-client carol-example --grant-types client_credentials \
  --scopes "read write" --source shared    --federated-read shared,customers,internal

# 注册完重启 serve
nohup env GBRAIN_HOME="<公司brain目录>" \
  gbrain serve --http --port 3131 > /tmp/gbrain-serve.log 2>&1 &
```

每个客户端注册成功后会返回 `client_id` + `client_secret`（凭证要妥善保存）。三个客户端的权限映射，就是三个人的角色边界：

| 客户端 | 写权限 (--source) | 读权限 (--federated-read) | 对应角色 |
|--------|------------------|--------------------------|---------|
| alice-example | customers | customers, shared | 销售：只碰客户与公共，碰不到内部敏感 |
| bob-example | internal | internal, shared | 运维：能读内部，碰不到客户私有 |
| carol-example | shared | shared, customers, internal | 法务 / HR：全 source 可读 |

> **注册数核验的坑**：`gbrain auth list` 显示的是 legacy bearer token，**不会**直接列出 OAuth confidential client。要核验三个 OAuth 客户端真的注册成功，看两处之一：
> - `gbrain doctor`：`oauth_confidential_client_health` 会显示 `3 OAuth client(s) registered`。
> - serve 重启后的 banner：会显示 `Clients: 3`。

> **PGLite 单写者坑（贯穿全程）**：PGLite 单写者引擎，`serve --http` 进程持有写锁。任何写操作（注册客户端、写页）在 serve 跑着的时候都会撞锁超时。记住套路：**写操作前先停 serve，写完再重启 serve**。

本环节产出：3 个 named source（各非空、100% 嵌入）+ 一个 `localhost:3131` 的 HTTP MCP OAuth 服务 + 3 个 scoped OAuth 客户端。隔离的「配置」全部就位，下一环节验证它「真生效」。

## 环节三：验证隔离真生效 + scoped think + 接入 AI 助手

配好了不等于生效。本环节用三套凭证跑同一条敏感查询，亲眼看到隔离对照，并机械核验零泄漏。这是整套方案的核心成果。

### 3.1 一个绕不过的环境前提：用 APFS、别用 exFAT

开始验证前，先确认你的 brain 放在合适的文件系统上。

> **文件系统坑**：PGLite 的 WASM 运行时在 **exFAT 文件系统**（常见于外置 SSD / U 盘）上不可靠，会报 `PGLite failed to initialize its WASM runtime`。这个错误的文案有时会误导你以为是 macOS 版本 bug，但**真正的根因是 exFAT 不支持 WASM 运行时需要的 mmap / POSIX 文件锁**。各种 workaround（复制、chmod、删锁文件、快照恢复）都无效，因为这是文件系统层的根本限制。
>
> **解法**：把 brain 放在 **APFS** 文件系统上。macOS 的 `/tmp` 就是 APFS，稳定可用。别把 brain 放在外置 exFAT 盘上。

另外注意，**OAuth 客户端是 brain-specific 的**：如果你换了一个新 brain（比如从 exFAT 挪到 APFS），旧 brain 上注册的 client ID 在新 brain 上全部失效，必须在新 brain 上重新 `register-client`。隔离取证前先确认这一点。

### 3.2 thin-client 模式：CLI 怎么接已被 serve 独占的 brain

既然 serve 进程独占了 PGLite 写锁，你用来做验证的 CLI 进程就不能再去初始化同一个 PGLite。GBrain 的 **thin-client 模式**解决这个：建一个含 `remote_mcp` 字段的 `config.json`，让 CLI 跳过本地 PGLite 初始化，直接路由到远程 MCP 服务。

```json
// 放在 $GBRAIN_HOME/.gbrain/config.json
{
  "remote_mcp": {
    "issuer_url": "http://localhost:3131",
    "mcp_url": "http://localhost:3131/mcp",
    "oauth_client_id": "gbrain_cl_..."
  }
}
```

几个工程细节：
- `GBRAIN_HOME` 会自动附加 `.gbrain/` 子目录，所以 config 要放在 `$GBRAIN_HOME/.gbrain/config.json`。
- CLI 检测到 `remote_mcp` 字段就走 thin-client 路由，跳过本地 PGLite。
- thin-client 的 CLI 文本输出**不支持 `--json`**，但**直接调 MCP HTTP API 能拿到带 `source_id` 的 JSON**——所以 source_id 的机械核验走 MCP HTTP API。
- **工业最佳实践**：MCP HTTP API 才是 teammate 真实的使用路径，CLI thin-client 是管理员的验证工具。

### 3.3 隔离对照取证（主成果）

三套凭证对同一条敏感查询「performance review」分别跑检索，逐行核验命中的 `source_id`。

先看 **Alice**（被授权读 customers + shared）的查询结果：她的 20 条结果**全部来自 customers 或 shared**，零 internal 命中——关键靶子页 `performance-review-2025-h1` **不在结果里**。

再看 **Bob**（被授权读 internal + shared）同一条查询：他**命中**了 internal source 的绩效页 `performance/performance-review-2025-h1`，`source_id=internal`。

同一条查询、不同凭证、不同结果——这就是隔离生效的铁证。核验逻辑是机械的，不靠肉眼判断「看起来对」：

| 凭证 | federated_read 授权 | 「performance review」命中的 source_id | 是否泄漏 |
|------|--------------------|-----------------------------------|---------|
| Alice | customers, shared | {customers, shared} | 否（零 internal） |
| Bob | internal, shared | {internal}（含绩效页） | 否（在授权内） |
| Carol | customers, internal, shared | {customers, internal} | 否（全在授权内） |

**核验规则**：每一条命中结果的 `source_id` 必须是该凭证 `federated_read` 集合的子集，任何一条越界即判 leak = FAIL。这套核验在 SQL 层强制 `source_id IN (...)`，而**不是**把所有结果都检索出来再让大模型过滤——后者正是工业反模式。

> **取证时的硬要求：靶子数据必须真实存在**。如果你的库里压根没有 internal source、没有绩效页，那「Alice 搜不到绩效」就变成平凡为真（库里本来就没有），毫无证明力。验证隔离时，敏感靶子必须真实存在于库中，且确实被 block，结论才有效。

> **关于规模与隔离的关系**：隔离机制是 scale-invariant（与数据规模无关）的——只要靶子页真实存在且真被 block，机制就成立，结论不受文件系统和页数影响。你可以先在一个小而真实的 brain（比如十几页、含真实 internal 靶子）上验证机制成立，再到 100 页的完整公司 brain 上补跑端到端取证。

### 3.4 写隔离：注意它是「路由」而非「报错」

读隔离之外，写也要隔离。Alice 的凭证注册时 `--source customers`，意味着她只能写进 customers source。测试让 Alice 尝试写一个标着 `internal/performance/leaked-data` 路径的页——结果这个页**被路由落到了 customers source，internal source 一个字节都没被改**。

> **一个与直觉不符、但必须清楚的机制细节**：GBrain 的写隔离**不是「拒绝越权写并报错」，而是静默地把写入路由到该凭证注册的 write_source**。Alice 想写 internal，东西实际落进了 customers。从安全结果看是对的（敏感 source 不被外人污染），但排查时要清楚：它的行为是「路由」而非「报错」，**别等一个拒绝异常**——异常不会来，你要核验的是实际落点。

### 3.5 scoped think：团队带 scope 的合成问答

隔离之上，是团队真正要用的体验——带 scope 的合成问答。Alice 问「acme-co 最近进展如何」，`gbrain think` 在她的 scope 内检索 + 合成。检索召回层会被 scope 限定，只在 Alice 授权的 source 内取页：

```bash
# 经 MCP HTTP API 调 think，记得开 no_expand 防多查询展开 bug（issue #1368）
curl -X POST localhost:3131/mcp -H "Authorization: Bearer $ALICE_TOKEN" \
  -d '{"method":"tools/call","params":{"name":"think","arguments":{"question":"acme-co 最近进展如何","no_expand":true}}}'
```

预期检索层结果：`pagesGathered=7`，召回的页**全在 Alice 授权的 source 内，零 internal 泄漏**，`no_expand=true` 已激活防展开保护。检索层的 scope 隔离完整生效。

> **两个 think 的注意点**：
> 1. **think 的 MCP 工具需要 `write` scope**（不只是 `read`），所以注册客户端时要给 `--scopes "read write"`，否则 think 调用会被拒。
> 2. **当前版本（v0.42.38.0）把 think 的 LLM 合成步骤硬编码到 Anthropic**，`models.think` 配置项在该版本不生效，没法切到 DashScope / DeepSeek。如果你的 Anthropic API 配额耗尽，能验证到的是 think 的**检索召回层 scope 隔离**（核心机制已成立），带 Citations 的合成答案要等配额可用、或等版本支持其它 provider 时才能跑出来。这是外部 API 限制，与隔离机制本身无关。

### 3.6 接入 AI 助手：证明 teammate 端真能用

最后证明 teammate 端真能用，而不只是在 CLI 里验证。把公司 brain 经 HTTP MCP + OAuth bearer token 接进 AI 助手（Claude Code / Cursor / Windsurf 等），让 AI 代替人去查：

```bash
# gbrain connect 一键生成 claude mcp add 命令
gbrain connect "http://localhost:3131/mcp" --token "$ALICE_TOKEN" --json

claude mcp add gbrain -t http "http://localhost:3131/mcp" \
  -H "Authorization: Bearer $ALICE_TOKEN" --scope user
# 然后在 AI 助手里直接让它用 gbrain 工具检索
```

用 Alice 的 token 接入后，AI 助手搜「acme-co」，返回的页**全部落在 Alice scope 的 customers source 内**。而库里明明有 internal source 和绩效页，AI **就是读不到**——scope 在 MCP 接入路径上和 CLI 路径上一样是 SQL 层强制。这是「连 AI 客户端也无法越权」的关键证据。

> **验证有效性的提醒（再强调一次）**：做这个证明时，fresh brain 里必须真实存在 internal source 和绩效页。如果库里本来就没有 internal，那「AI 看不到 internal」是平凡为真、毫无意义。先往库里注入真实的敏感靶子，再证明 AI 仍读不到——这才是有效的隔离证明。

本环节取证：三客户端隔离对照零泄漏（source_id 机械核验）+ 写隔离（路由而非拒绝）+ scoped think 检索层 scope 生效 + AI 助手 over MCP 的 scoped 真隔离。核心成果达成。

## 关键认知与踩坑小结

### 一句话核心认知

**访问控制必须落在数据库层，不能靠大模型自觉。** 隔离是 SQL 层 `federated_read` 对 `source_id` 的强制过滤，每一条结果的 `source_id` 都能机械核验是否在授权集内，任一越界即判泄漏。这是 2026 多租户 RAG 的工业共识：用大模型做访问控制是反模式。

### 踩坑速查表

| 坑 | 现象 | 解法 |
|----|------|------|
| GBRAIN_HOME config 写入歧义 | `gbrain config set` 写进默认 `~/.gbrain`，公司 brain 配置不生效，import 全 auth fail | 用 `python3` 直接把 `provider_base_urls` 写进公司 brain 自己的 `config.json` |
| sync 要 git 仓库 | `gbrain sync` 对普通目录报 "Not a git repository" | 各 corpus 子目录先 `git init` + commit |
| import --source 静默失效 | `gbrain import --source <id>` 不路由，页面全进 default、不报错 | source 路由必须走 `gbrain sync`，不能用 `import --source` |
| PGLite 单写者锁 | serve 在跑时 `auth register-client` 超时（"Timed out waiting for PGLite lock"） | 先停 serve → 注册 → 重启 serve |
| exFAT 上 PGLite WASM 失败 | 报 `PGLite failed to initialize its WASM runtime`，错误文案误导成 macOS 版本 bug | brain 放 APFS（macOS `/tmp` 可靠），别放 exFAT 外置盘 |
| OAuth 客户端 brain-specific | 换 brain 后旧 client ID 全失效 | 在目标 brain 上重新 `register-client` |
| 写隔离是路由非拒绝 | 越权写不报错，静默落到 write_source | 排查时核验实际落点，别等拒绝异常 |
| think 需 write scope | think MCP 工具仅给 read scope 会被拒 | 注册时给 `--scopes "read write"` |
| think 合成硬编码 Anthropic | `models.think` 配置在 v0.42.38.0 不生效，无法切 DashScope | 确保 Anthropic API 有配额，或等版本支持其它 provider |
| auth list 不列 OAuth client | `gbrain auth list` 只显示 legacy bearer token，看不到 OAuth client | 核验 OAuth 客户端数看 `gbrain doctor` 或 serve banner 的 `Clients: N` |
| MCP HTTP 返回 SSE 格式 | 响应是 `data: {...}` 含控制字符，无法直接 `json.loads` | 抓到文件、取 `data: ` 偏移后再 `json.loads` |

### 完整命令清单（按环节）

```bash
# === 环节 1：语料 + 建库 ===
GBRAIN_HOME="<brain>" gbrain init --pglite \
  --embedding-model dashscope:text-embedding-v3 --embedding-dimensions 1024
GBRAIN_HOME="<brain>" gbrain import corpus/
GBRAIN_HOME="<brain>" gbrain stats
GBRAIN_HOME="<brain>" gbrain doctor
# 迁 Postgres（装了 Docker 时）
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres pgvector/pgvector:pg16
DATABASE_URL=postgres://postgres:postgres@localhost:5432/gbrain gbrain migrate --to supabase

# === 环节 2：切 source + serve + OAuth ===
gbrain sources add shared    --path corpus/shared    --name "Shared company wiki"
gbrain sources add customers --path corpus/customers --name "Customer notes"
gbrain sources add internal  --path corpus/internal  --name "Internal-only"
cd corpus/<ns> && git init && git add . && git commit -m "x"   # 每个 source 目录
gbrain sync --source <ns> --no-pull                            # 每个 source
gbrain sources status
gbrain serve --http --port 3131 &
curl localhost:3131/health
kill -TERM $(pgrep -f "gbrain serve")                          # 注册前停 serve
gbrain auth register-client <member> --grant-types client_credentials \
  --scopes "read write" --source <write_ns> --federated-read <read_ns1,read_ns2>
gbrain serve --http --port 3131 &                              # 注册后重启
gbrain doctor                                                  # 核验 Clients: 3

# === 环节 3：隔离验证 + think + AI 助手 ===
# 隔离检索（看每行 source_id）：用各成员凭证经 MCP HTTP API 查同一条敏感词
curl -X POST localhost:3131/mcp -H "Authorization: Bearer $TOKEN" \
  -d '{"method":"tools/call","params":{"name":"search","arguments":{"query":"performance review"}}}'
# scoped think（no_expand 防 #1368）
curl -X POST localhost:3131/mcp -H "Authorization: Bearer $TOKEN" \
  -d '{"method":"tools/call","params":{"name":"think","arguments":{"question":"...","no_expand":true}}}'
# AI 助手 over MCP
gbrain connect "http://localhost:3131/mcp" --token "$TOKEN" --json
claude mcp add gbrain -t http "http://localhost:3131/mcp" -H "Authorization: Bearer $TOKEN" --scope user
```

## 换个团队怎么迁移这套骨架

这套方案的骨架与具体业务无关，换个团队、换套权限映射即可复用。核心改造点：

| 改造维度 | 改什么 |
|---------|-------|
| source 划分 | 把 `shared / customers / internal` 换成你的命名空间，敏感层放真实靶子数据 |
| 人 → scope 映射 | 把 alice/bob/carol 的 `--source` / `--federated-read` 换成你团队成员的角色权限 |
| 语料 schema | 把客户合同金额 / 绩效评分 / 会议结论等字段换成你领域的结构化字段 |
| 关系网络 | 把人↔公司↔会议↔决策的 wikilink 换成你领域的实体关系 |
| 后端 | 单人测试用 PGLite，多人生产迁 Postgres |

几个能直接套的场景：

- **律所 / 会计师事务所**：合伙人 / 律师 / 行政三层，案件按 source 隔离，**利益冲突墙**（ethical wall）就用 source scope 实现——负责 A 案的律师搜 B 案关键词应当零命中。
- **咨询公司**：项目组 A / 项目组 B / 共享方法论库，跨项目数据按客户隔离。
- **医疗 / 研究机构**：临床数据 / 科研数据 / 公开资料三层，受监管的患者数据按 source 强隔离。
- **任意「共享知识 + 敏感分层」团队**：把「公共层 / 个人 scope / 敏感内部层」三层结构映射进来即可。

以「律所利益冲突墙」为例的完整命令：

```bash
gbrain sources add matters-acme     --path corpus/matters-acme    --name "Acme 案件卷宗"
gbrain sources add matters-zenith   --path corpus/matters-zenith  --name "Zenith 案件卷宗"
gbrain sources add shared-precedent --path corpus/precedent       --name "公共判例库"

# 负责 Acme 案的律师：只能读自己案件 + 公共判例，碰不到 Zenith 案（利益冲突墙）
gbrain auth register-client lawyer-on-acme --grant-types client_credentials \
  --scopes "read write" --source matters-acme \
  --federated-read matters-acme,shared-precedent
# 合规官：全卷可读
gbrain auth register-client compliance-officer --grant-types client_credentials \
  --scopes "read write" --source shared-precedent \
  --federated-read shared-precedent,matters-acme,matters-zenith
# 验证：lawyer-on-acme 搜 Zenith 案关键词应零命中（ethical wall 生效）
```

骨架完全一致，把命名空间和成员角色换成你的就行。隔离验证方法也通用：每个成员凭证查一条只有授权 source 才该命中的敏感词，逐行核验 `source_id` 必属该成员 `federated_read` 集，任一越界即 leak = FAIL。
