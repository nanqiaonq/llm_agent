# 混合架构实现指南：编译式 wiki 大脑 + 向量 RAG 并用

> 这是第三节课的进阶自学材料。前面我们已经搭好了自己的「个人大脑」（GBrain），会建库、查询、接 MCP、做维护。主课件 §7.2 提到「混合架构：编译 wiki + 向量 RAG 并用、路由复杂度」，本指南就是它的完整落地版——带你从零搭一套**编译式 wiki + 外部向量 RAG** 的混合知识系统。

---

## 一、这份指南讲什么，什么时候需要它（以及什么时候不需要）

### 1.1 一句话说清混合架构

你已经有了一个编译式大脑：它把稳定的知识编译成互相链接的 wiki 页面，做高质量的跨页合成，回答「为什么这样设计」这类需要综合多页的问题特别强。但它有个天生短板——**每次内容变动都要重新编译**。

而现实里的知识其实是两类截然不同的东西：

- **稳定的核心知识**：「我们的认证架构为什么选 JWT？」「文档导出端点有哪些请求参数？」「数据保留政策怎么规定的？」——这些写定后长期不变，是设计基线。
- **易变的长尾事实**：「上周有没有用户报登录相关的工单？」「2.4.2 版本的 changelog 改了什么？」「上次工程例会决定了什么？」——这些每天都在产生、快速演变。

把这两类塞进同一套系统会两头不讨好：编译式 wiki 承受不了工单、changelog 这种高频增量（每改一次就要重编译）；而纯向量 RAG 虽然能吞海量易变文档，但对「为什么选 JWT」这种要跨多页综合的稳定设计问题，召回质量和权威性又不如编译式 wiki。

**混合架构的解法是不二选一**：让两套系统各管一摊——稳定核心知识走编译式 wiki 大脑，易变长尾文档走外部向量 RAG；前面再放一个**查询路由器**按问题类型分流；遇到跨界问题（既问稳定设计、又问近期事实），就同时查两边，融合成一个**带来源标注**的统一答案。

### 1.2 什么时候你才真的需要它

这是本指南最该先讲清楚的边界，否则你会过度工程：

> **先用单源（GBrain only）把业务跑通，确认单源真的不够用，再上混合架构。**

混合架构**不是免费的「更好」**。它给你的不是「总召回率更高」的童话，而是一个非常具体的能力：**在跨界综合型查询上，同时拿到 wiki 的权威稳定设计 + RAG 的近期事实**。代价我们后面会反复讲——主要是路由复杂度。

判断标准很简单，问自己一句：

- 我的知识里是不是**真的同时存在稳定层和易变层**？（比如稳定的架构设计文档 + 每天新增的工单/日志/会议纪要）
- 单纯用 GBrain，是不是已经被「易变数据重编译成本」逼到墙角了？

如果你的知识基本都是稳定的，或者易变部分小到可以接受重编译——**那就别上混合架构，单 GBrain 足够**。多一套系统就多一份路由、融合、调试的负担。

### 1.3 一个必须先分清的概念：两个「hybrid」不是一回事

「hybrid（混合）」这个词会出现两次，含义完全不同，开篇就分清，后面才不会乱：

| 名称 | 含义 |
|------|------|
| **大脑内 hybrid** | GBrain 单个大脑**内部**把向量检索（HNSW）+ 关键词检索（BM25）两路用 RRF 融合。这是 GBrain 本身就有的能力，你查询时一直在用它，本指南**不重讲它的原理**，直接当成 wiki 路的输入。 |
| **架构级 hybrid** | 编译式 wiki 系统 与 外部向量 RAG 系统 **两个不同系统之间**的混合（路由 + 跨系统二次融合）。**这才是本指南的主角。** |

> **RRF**（Reciprocal Rank Fusion，倒数排名融合）：一种按「排名」而非「原始分数」来合并多路检索结果的算法。本指南里它出现在两层：第一层是 wiki 大脑内部的融合（GBrain 自带，你不用管）；第二层是架构级融合（本指南新增，融合 wiki 系统和 RAG 系统两个排序列表）。后文每次提到 RRF，都会说清是哪一层。

## 二、整体架构与数据流

整套系统由四个环节串成，数据是强依赖的，一步接一步：

```
环节 1：双源建库      →  环节 2：查询路由     →  环节 3：双路检索 + 架构级融合  →  环节 4：端到端混合问答
（wiki 侧 + RAG 侧）     （按类型分 wiki/rag/both）  （RRF 融合 + 来源标注）          （喂 LLM 合成带来源的答案）
```

为了让示例有真实业务感、又零隐私风险，下面用一个虚构的协作文档 SaaS 产品「DocFlow」做载体。所有知识都围绕这一个产品域展开——**两侧同属一个产品域，是后续融合能成立的前提**：

- **wiki 侧**写 DocFlow 的稳定核心：架构设计决策、API 端点规格、团队组织、安全与发布政策。
- **RAG 侧**写 DocFlow 的易变长尾：用户支持工单、changelog 条目、工程会议纪要、生产事故报告。

下面按环节展开，每步给说明 + 命令/配置。

---

## 三、环节 1：双源知识基建

这一步要同时建成两套库。wiki 侧你已经熟了（就是你的 GBrain），这里只讲混合场景下的两点新要求；RAG 侧是全新内容，从零讲。

### 3.1 wiki 侧：稳定核心知识

wiki 侧还是你熟悉的 `gbrain init / import / doctor` 那套命令链。混合场景下和单源演示有两点差异：

- **数据规模**：要导入足量的稳定知识才有意义。本示例导入 **60 页同一产品域的稳定知识**，分四类目录——`architecture/`（认证/存储/部署设计决策）、`api-specs/`（端点规格）、`team/`（组织/职责）、`policies/`（安全/发布/数据政策）。
- **互链**：60 页之间用 `[[wikilink]]` 互链（如 `[[auth-design]]`、`[[team-platform-engineering]]`），import 后 GBrain 会零 LLM 自动建出带类型的边（typed edges）。这是 GBrain 的图自动建边能力，你建库时本来就在用。

建库命令（这里用 DashScope 的 `text-embedding-v3` 做 embedding，1024 维）：

```bash
# 旧 brain 可能因引擎版本不兼容报 WASM Aborted，重建最干净
rm -rf ~/.gbrain
gbrain init --pglite --embedding-model dashscope:text-embedding-v3 --embedding-dimensions 1024 --non-interactive
# ⚠️ 关键：init 重建后 config.json 会缺这个端点字段，必须手动补，否则 DashScope embedding 直接失败
gbrain config set provider_base_urls.dashscope https://dashscope.aliyuncs.com/compatible-mode/v1
```

导入并 embed：

```bash
DASHSCOPE_API_KEY=... GBRAIN_MODEL=deepseek:deepseek-chat gbrain import '<你的 wiki 目录>'
```

import 完成后这个库含 60 页、67 个 chunk。

> 小坑：`gbrain list` 默认只显示 50 条（`limit=50`），要看全得加 `--limit 100`。

**wiki 侧状态判别**：

```bash
gbrain doctor
```

期望看到：`Connected`、`60 pages`、`100% coverage`、`0 missing`、`text-embedding-v3 1024 dims`、`DB aligned`、`No stale chunks`。

> 这里有个会让你困惑的点：doctor 报告的 `Overall health score` 可能是 45/100，并不是满分——这是因为 PGLite 模式跳过了只有 Supabase 后端才有的检查项（oversized_pages、scraper_junk_pages），属于**预期现象，不是建库失败**。真正绑定验收的三项——`Connected`、`100% embed coverage`、`1024 维对齐`——全绿就达标。PGLite 模式下 doctor 本来就拿不到满分。

### 3.2 RAG 侧：从零自建向量检索库（本指南核心新增）

RAG 侧用 **ChromaDB**（开源向量数据库，官网 [trychroma.com](https://www.trychroma.com)、GitHub [chroma-core/chroma](https://github.com/chroma-core/chroma)），用它的 `PersistentClient` 做本地持久化。

**最关键的设计**：RAG 侧必须和 wiki 侧用**同一个 embedding 模型**（这里都是 DashScope `text-embedding-v3`、1024 维）。只有这样，两套系统的向量才落在同一个几何空间里，后面融合时分数才可比。

核心是写一个自定义 embedding function，把 query 和文档发到 DashScope 兼容端点，拿回 1024 维向量，再写进 ChromaDB collection。建库参数：

- collection 名：`docflow-rag-volatile`
- embedding：`dashscope:text-embedding-v3`，1024 维
- 产品域标记：`product_domain = docflow-saas`
- 文档切 chunk：`chunk_size=100`、`overlap=20`

本示例把 **105 个易变长尾文档**切成了 **1172 个 chunk**，四种文档类型的分布是：

```
总 chunk 数：1172
  ├─ support-ticket   （用户支持工单）   414
  ├─ changelog        （变更记录）       391
  ├─ incident-report  （事故报告）       292
  └─ meeting-notes    （会议纪要）        75
```

建库后做个验收：`collection.count()` 要达到你设的 chunk 门槛（本示例门槛 ≥ 500，实际 1172，通过）。再用一条 query 测一下，比如 `DocFlow authentication JWT token session`，应该能返回语义相关的 support-ticket + incident-report 结果——能返回，RAG 侧就建成功了。

### 3.3 确认双源互补、分数可比

环节 1 结束时，用同一个词（比如 `token`）分别查两源，确认它们知识互补、且分数可比（这是环节 3 跨系统融合的几何前提）。预期效果：

- **wiki 侧**返回稳定的 policy / architecture 页（如 `token-rotation-policy`、`auth-design`）；
- **RAG 侧**返回易变的工单 / 变更条目（如 `ticket-AUTH-002`、`INC-2026-045`）。

同一个词，两源各自给出自己擅长的那一类知识——这就是互补，混合架构的价值地基。

双源终态对照：

| 维度 | wiki 侧（GBrain） | RAG 侧（ChromaDB） |
|------|------------------|--------------------|
| 规模 | 60 页 / 67 chunk | 105 文档 / 1172 chunk |
| embedding | text-embedding-v3 / 1024 维 | text-embedding-v3 / 1024 维 |
| 产品域 | docflow-saas | docflow-saas |
| 内容 | 稳定核心知识 | 易变长尾数据 |

### 3.4 环节 1 的真实踩坑

这一步实测踩到四个坑，都有价值：

| 坑 | 现象 | 解法 |
|----|------|------|
| 引擎版本不兼容 | 旧 `brain.pglite` 报 WASM Aborted | `rm -rf ~/.gbrain` 重建 |
| config 缺端点 | 重建后 `config.json` 缺 `provider_base_urls.dashscope`，DashScope embed 失败 | 手动 `gbrain config set` 补加国内端点 |
| **DashScope batch_size 上限是 10** | `text-embedding-v3` 走 compatible-mode/v1 时，一批传 20+ 文档 → 报 400 BadRequestError | 自定义 embedding function 的 `__call__` 里把 batch_size 设为 **10**（不是 25） |
| 磁盘满装不上 chromadb | 项目所在盘满了 | 换个有空间的盘建虚拟环境，ChromaDB 持久化目录也放有空间的路径 |

> 其中 **DashScope `batch_size ≤ 10`** 是你复刻 RAG 侧几乎必踩的坑，务必记住。另外注意：如果你把 ChromaDB 持久化目录放在 `/tmp/` 这类临时路径，机器重启后会被清空——做实验图方便可以，**生产环境一定要放稳定路径**。

### 3.5 一个贯穿全程的属性：双源语言可以异构

本示例 wiki 侧语料是中文、RAG 侧语料是英文。`text-embedding-v3` 是**多语言模型**，能跨语言算相似度，所以两源向量仍落在同一几何空间、融合可比；但跨语言 query 的 distance 会偏高一点。如果你换自己的数据时双源语言不同，留意这一点即可。

### 3.6 换业务场景时改什么

- **双源域定义**：把 `docflow-saas` 换成你的产品/领域，保证两源同域。
- **wiki 类型**：把四类目录改成你的稳定知识分类。
- **RAG 文档类型**：改成你的易变长尾数据类型。
- **embedding 模型**：双源必须用同一个，换模型时两侧同步换。

## 四、环节 2：查询路由器（混合架构的灵魂，也是复杂度的来源）

「按查询类型路由」是混合架构的灵魂——也正是它带来了**核心代价：路由复杂度**。query 必须被分到对的系统，路由错了，比单源系统更难调试（因为你得先判断到底是检索错了还是路由错了）。这一节我们既讲怎么做，也诚实讲它的边界。

我们自建一个 `router.py`，用 LLM zero-shot（零样本，不喂训练样本、直接让模型按描述分类）做三分类、规则兜底、默认 `both` 保召回。LLM 分类这里调 DeepSeek。

### 4.1 路由器的三层逻辑

`classify_query(query, api_key)` 返回 `{'label': 'wiki'|'rag'|'both', 'method': 'llm'|'rule_fallback', ...}`，逻辑分三层：

1. **LLM zero-shot 分类（主路径）**：把 query + 两源描述喂给 DeepSeek，让它输出三类标签之一。
2. **规则关键词兜底**：LLM 返回非法标签或超时，就用关键词规则——含「最近/上周/工单/changelog」等易变信号词 → `rag`；含「为什么/架构/设计/规格」→ `wiki`。
3. **默认 both**：还是不确定，就默认 `both`，双路都查保召回（误判不致命，因为 both 反正两边都查）。

三类查询对应三种路由：

- 稳定核心型（「认证架构为什么选 JWT」）→ `wiki` → 只走 wiki 路。
- 易变长尾型（「上周有没有登录 bug 工单」）→ `rag` → 只走 RAG 路。
- 跨界综合型（「认证怎么设计的、最近又有没有登录问题」）→ `both` → 双路检索 + 架构级融合。

### 4.2 路由质量高度依赖「两源描述文案」

这是你做混合架构最该上心的地方：路由判得准不准，**主要取决于你给两源写的描述文案**有多准。本示例的描述是：

- **wiki 描述**：「稳定核心知识库（编译式 wiki）：包含 docflow-saas 的架构设计决策（认证/存储/部署）、API 端点规格、团队组织结构、安全与发布政策。这些内容变动极少，版本稳定。」
- **rag 描述**：「易变长尾知识库（向量 RAG）：包含 docflow-saas 的用户支持工单、changelog 更新记录、工程会议纪要、生产事故报告。这些内容频繁产生、随时间演变。」

换场景时，把这两段描述改成准确刻画你自己两源覆盖范围的文案——这直接决定路由质量。

### 4.3 一个隐蔽的坑：推理模型把 token 耗在「思考」上

这一步最有价值的坑：如果你的 DeepSeek 用的是**推理模型**（比如 `deepseek-v4-flash`），它会先在 `reasoning_content` 字段里做链式推理（大约 187 token），再在 `content` 字段产出实际答案。

如果你把 `max_tokens` 设太小（比如 10 或 200），所有 token 全耗在推理上、`content` 字段是空字符串，你的 LLM 分类结果根本提取不出来，于是**静默回落到规则兜底**：

```
现象：max_tokens=10  →  content=''  →  静默回落规则兜底
根因：推理还没做完就被 max_tokens 截断，content 永远为空
修复：max_tokens 改为 1500（推理约 187 token + 输出留余量），timeout 改 60s
```

> 这个坑最坑的地方是**它不报错**，只是默默不走 LLM 路径。如果你不知道推理模型的 token 分配机制，会以为路由器在正常工作，实际上 LLM 分类从未生效。换用推理模型时，`max_tokens` 务必留足推理余量（建议 ≥ 1500）。

### 4.4 路由评测怎么做，以及它的真实边界

**评测方法**：设计 ≥ 9 条标注测试 query（三类各 ≥ 3 条），跑路由分类，产出一张对照表（query / 预期类 / 实际类 / 是否走兜底），算准确率。

这里要诚实给你看**两组真实数据**，它们的差异本身就是最重要的教学点：

**第一组（措辞清晰的标注集）**：11 条 query 路由准确率 **11/11（100%）**，其中 10 条走 LLM 分类、1 条走规则兜底，三类标签全部出现。

**第二组（端到端阶段另一组 9 条 query）**：准确率掉到 **6/9（66%）**，具体是：

- wiki 型 3/3（100%）正确；
- rag 型 3/3（100%）正确；
- **both 型 0/3（0%）全部被误判成了 `wiki`**。

为什么 both 型全错？因为这组 both 型查询都用了 wiki 域的术语（如「JWT」「架构」「设计」），LLM 按描述文案判定它们是稳定知识，给了 `wiki` 标签。这暴露了 zero-shot 路由的一个**真实局限**：

> **当一个跨界查询的措辞偏向某一源时，路由器会倾向那一源。**

这两组数字（100% 与 66%）不矛盾，而是真实工程现实：**路由准确率高度依赖测试集的措辞分布**。把它诚实摆出来，你才知道 zero-shot 路由的边界在哪。

**这正是「路由复杂度」这个核心代价的具体形态**：当跨界 query 的 `both` 路由判不准时，你有两个选择：

1. 接受边界，**用纯 wiki 域术语的查询显式触发 full fusion**，或者直接调用双路融合函数（不依赖路由器自动给 `both`）——这是本示例的做法。
2. 上 **query decomposition**（查询拆解）：把跨界查询拆成 wiki 子查询 + rag 子查询分别发送。这是真实生产里更彻底的解法，但实现成本高，作为进阶方向，本指南不展开实现。

### 4.5 换业务场景时改什么

- **两源描述文案**：重写 `wiki_description` / `rag_description`，准确刻画你两源各覆盖哪类知识。
- **推理模型 token**：换推理模型记得 `max_tokens ≥ 1500`。
- **兜底关键词**：把易变/稳定信号词改成你领域的关键词。
- **验证**：≥ 9 条标注 query 跑路由，三类标签都出现、准确率可算、误判有兜底。

## 五、环节 3：双路检索 + 架构级 RRF 融合 + 来源标注

这一步是「两层 RRF」概念真正落地的地方。我们写一个 `fusion.py`，实现三件事：wiki 路检索、RAG 路检索、架构级 RRF 融合 + 来源标注（provenance）。

### 5.1 wiki 路检索

wiki 路就是调你的 `gbrain query --no-expand`，把它的检索结果当成架构级融合的**一路输入**。探针命令：

```bash
# 必须用 perl alarm（或 timeout）包装、且不走管道
perl -e 'alarm 30; exec @ARGV' -- gbrain query '认证架构 JWT 设计决策' --no-expand --limit 5 2>&1
```

> 两个注意点（你查询 GBrain 时本来就该知道）：
> - **必须加 `--no-expand`**：默认的 `--expand` 会触发多查询扩展，可能把 CPU 跑挂。
> - **必须用 `perl -e 'alarm 30'`（或 `timeout -k 5 30`）包装、且不走管道**，给它一个超时上限，避免卡死。

`wiki_retrieve()` 把 gbrain query 的输出解析成 `[{rank, slug, score, source_system:'wiki'}]` 这样的 ranked list（优先用 `--json`，不支持就正则取页序——因为 RRF 只需要顺序，容错很高）。

### 5.2 RAG 路检索

`rag_retrieve()` 先用 DashScope `text-embedding-v3` 把 query embed 成 1024 维向量，再调 `collection.query(query_embeddings=...)`，返回 `[{rank, chunk_id, content, distance, source_system:'rag'}]`。

> **这里有个必踩的维度坑**：如果你图省事用 `collection.query(query_texts=...)`，ChromaDB 会触发它**内置的 all-MiniLM-L6-v2（384 维）**去做 embedding，和你建库时的 1024 维不匹配，直接报错：
>
> ```
> Collection expecting embedding with dimension of 1024, got 384
> ```
>
> **必须用 `query_embeddings=[<你自己算的 1024 维向量>]`**，把 embedding 显式握在自己手里，不要让 ChromaDB 自作主张。

### 5.3 架构级 RRF 融合（第二层 RRF）

`rrf_fuse(wiki_results, rag_results, k_const=60)` 把两路 ranked list 按 `score = Σ 1/(k_const + rank)` 合并，每条标上 `source_system`。这是**第二层 RRF**，和大脑内 RRF 不是一回事：

| 维度 | 大脑内 RRF（GBrain 自带） | 架构级 RRF（本指南新增） |
|------|--------------------------|--------------------------|
| 融合对象 | 同一大脑内的向量路 + BM25 路 | wiki 系统 与 RAG 系统两个异构系统 |
| 层级 | 系统内部 | 系统之间 |
| 输入 | 两路 chunk 排名 | 两个系统的 ranked list |

`k_const=60` 是 Cormack & Clarke 2009 的推荐值。

> 一个常见疑问：**为什么用 rank（排名）不用 score（原始分数）？** 因为 wiki 系统的相关度分数，和 RAG 系统的向量 distance，量纲完全不同、跨系统根本不可比。RRF 用排名而不是原始分数，正好绕开了「跨异构系统怎么把分数归一化」这个难题。这就是融合层用 RRF 的根本原因。

### 5.4 完整融合演示与来源标注

集成后，用一条核心 both 查询 `DocFlow JWT auth design architecture security` 跑端到端融合。真实结果：

```
fusion_mode = full
  wiki 路返回：1 条
  RAG  路返回：5 条
  ──────────────────
  融合后：6 条统一排序，每条都带 source_system 标注（覆盖率 100%）
```

每条结果都标注了它来自 wiki 还是 RAG——这就是 **provenance（来源溯源）**，它正好补回了编译式系统在「可溯源」上的短板。

> 注意：**wiki 路只命中 1 条，不是「两路各 5 条饱满融合」**。这不是 bug，是 GBrain 的真实行为，原因见下面 5.5。

### 5.5 最重要的工程发现：BM25 跨域查询的 AND 匹配失败 + 降级

这是核心演示里 wiki 只命中 1 条的根因，也是这一步最该记住的坑：

```
现象：gbrain query --no-expand '认证设计和最近的登录相关工单'  →  No results
根因：GBrain 的 BM25 对多词查询要求「所有 token 都命中」。
      wiki 语料是稳定产品设计知识，不含「工单/incidents」这类 RAG 域的易变词
      →  跨域查询在 BM25 上 0 命中  →  融合降级为 rag_only
```

还有个相关现象：GBrain 的 tokenmax 模式 autocut——多词查询里含低信号词时整体置信度下降，autocut 会把结果直接截为空（比如 `auth JWT design architecture and recent login issues` → No results）。

这带来一个真实的业务分支：**当 both 查询的 wiki 路 0 结果时，融合要降级为 `rag_only`（单路），并文档化「wiki 路无命中」**。所以本示例的核心演示刻意用纯 wiki 域术语（`JWT/auth/design/architecture`）的查询来触发 full fusion，让 DashScope embedding 负责把语义跨域到 RAG 侧。

**降级处理是必做的错误处理**。你的融合逻辑要覆盖三种分支：

1. 两路都有结果 → 正常融合；
2. 某路 0 结果 → 降级为单路 + 文档化说明；
3. 两路都 0 → 落「双源此项为空」。

> 更彻底的生产解法仍然是 query decomposition：把跨界查询拆成 wiki 子查询和 rag 子查询分别发送，各打各的。本指南不实现，作为进阶方向告诉你。

### 5.6 换业务场景时改什么

- **wiki 路解析**：换大脑时确认 `gbrain query` 的输出字段，调整解析逻辑（优先 `--json`）。
- **RAG 路 embedding**：始终用 `query_embeddings=` 显式传向量，避免触发 ChromaDB 内置的 384 维模型。
- **RRF k 值**：默认 60，需要时可做 k 参数扫描微调。
- **降级处理**：一定要实现「某路 0 结果」的降级分支，跨域查询在生产里很常见。

## 六、环节 4：端到端混合问答 + 三形态对照 + 诚实成本

这一步把前三个环节串成完整闭环，并产出两张最能说明「该不该上混合架构」的结果。

### 6.1 端到端混合问答（带来源标注的合成）

把融合后的 top-k 结果（含来源标注）当作 context，喂给 DeepSeek 合成一个统一答案，并要求模型**对每段标注来源系统**。

真实效果：合成耗时约 7.0s，输出带 `[来自 wiki]` / `[来自 RAG]` 的段级来源标注——稳定设计的部分标注来自 wiki，近期事实的部分标注来自 RAG。一个问题，两套系统协同回答，而且**每一句都知道它从哪来**。

这正是 §1.1 那个核心成果：向系统问「我们的认证架构怎么设计的、为什么选 JWT，而且最近一周有没有用户报登录相关的问题？」——系统把它当成跨界综合型查询，同时查 wiki（取稳定的认证架构设计页）和 RAG（取近期的登录工单），融合后产出一个每句都标来源的统一答案。

> 合成 prompt 里要求模型对每段标来源系统，是工业级可溯源的关键，别省。

### 6.2 三形态对照：为什么要混合（以及它不是什么）

把同一组测试 query，分别用「纯 wiki」「纯 RAG」「混合路由」三种形态各跑一遍，记录命中率。真实数据：

```
三形态命中率对照：
  纯 wiki    ████                          0.11
  纯 RAG     ████████████████████████████  1.00
  混合路由   ███████████                   0.44
```

**这组数字没有呈现「混合 = 总命中率最高」的童话**，必须正确解读：

- 测试集里 RAG 域的易变长尾问题占多数，所以纯 RAG 原始命中率最高。
- wiki 的 BM25 召回率天然偏低（精确匹配为主），所以纯 wiki 命中率最低。
- **混合架构的真正价值不在「总召回率最高」，而在于：跨界综合型查询上能同时拿到 wiki 的权威稳定设计 + RAG 的近期事实**——这是纯 wiki、纯 RAG 任一单形态都做不到的。

换句话说，混合保证的是「稳定知识走 wiki 拿到权威答案」这条**质量底线**，而不是堆高一个总召回数字。这是选型的核心：**别指望混合架构全面碾压单源**，它换来的是跨界质量，代价是路由复杂度。

### 6.3 诚实成本：路由依据不是「省 token」

有个常见误印象是「编译式比向量 RAG 省成本」。真实数字（来自 arxiv 2605.18490）：

```
编译式查询消耗 token：≈ 1,651,357
向量 RAG 查询消耗 token：≈    78,947
                          ──────────
编译式约为向量 RAG 的：    21 倍
```

所以把易变长尾数据路由到 RAG，**依据不是「编译省 token」**（恰恰相反，编译式查询贵得多），而是两条真实理由：

- **易变数据重编译成本高**：工单、changelog 每天增量，走编译式 wiki 每次都要重新编译，代价不可接受；走 RAG 只需增量 embed 入库。
- **突破编译式的规模天花板**：编译式 wiki 适合少而精的稳定核心层，海量易变长尾层交给 RAG 承担规模。

> 一句话记住：**编译式 wiki 的优势是「跨源合成质量 + 可溯源」，不是成本。** 别把混合架构当成省钱方案。

### 6.4 一个诚实的数据偏差

实测时有处偏差要如实告诉你：前面环节 `gbrain doctor` 报告 60 页，但端到端阶段 `gbrain list` 只看到 50 页。原因没完全定位（可能和 PGLite 在不同会话的状态有关）。50 页仍覆盖四个类型，端到端演示能正常跑通，所以不阻塞——你复刻时若看到页数有出入，属于已知现象。

### 6.5 环节 4 的踩坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 函数签名不符 | `classify_query()` 传 `timeout_s` 报 unexpected keyword | 移除该参数（签名是 query/api_key/credentials_path/verbose） |
| `rag_limit=0` 崩溃 | `dual_retrieve_and_fuse(rag_limit=0)` → ChromaDB 报「requested results 0」崩溃 | 三形态对照里的纯 wiki / 纯 RAG 形态，直接调 `wiki_retrieve()` / `rag_retrieve()`，别走融合入口 |
| 跨域核心查询无命中 | 跨域核心查询 → wiki 路 0 结果 | 改用环节 3 验证过的纯 wiki 域词 both 查询 |

## 七、选型与踩坑小结

### 7.1 该不该上混合架构：决策清单

按顺序问自己：

1. **我的知识是不是真的同时有稳定层和易变层？** 否 → 不用混合，单 GBrain 足够。
2. **单源（GBrain only）跑通了吗？是不是真被「易变数据重编译成本」逼到墙角了？** 没跑通 / 没被逼到 → 先用单源，别提前上混合。
3. **我能不能承受路由复杂度这个代价？** 路由错误比单源更难调试（要先分清是检索错还是路由错）。承受不了就别上。

三条都是「是」，再上混合架构。**混合架构不是免费的更好——它用路由复杂度，换来跨界综合型查询上的质量底线和可溯源。**

### 7.2 三条不能动摇的设计约束

- **双源必须同一个 embedding 模型 + 同一个产品域**：否则两套系统的向量不在同一几何空间、不在同一业务域，融合既不可比也没业务意义。
- **融合层用 rank-based RRF**：跨异构系统的分数量纲不可比，用排名绕开归一化难题。
- **必须实现降级分支**：某路 0 结果时降级单路并文档化，跨域查询在生产里很常见，不处理就会崩或给出空答案。

### 7.3 全程关键踩坑汇总

| 环节 | 坑 | 根因 | 解法 |
|------|----|----|----|
| 建库 | DashScope `batch_size ≤ 10` | compatible-mode/v1 上限是 10 非 25，传 20+ → 400 | embedding function 内 batch_size 设 10 |
| 建库 | 重建 brain 后 config 缺端点 | `gbrain init` 不写 `provider_base_urls.dashscope` | 手动 `gbrain config set` 补加 |
| 路由 | 推理模型 content 为空 | 推理模型先做 reasoning，`max_tokens` 太小则 content='' | `max_tokens` 改 1500、timeout 60s |
| 融合 | ChromaDB 维度不匹配 1024 vs 384 | `query_texts` 触发内置 384 维 MiniLM | 用 `query_embeddings=[1024 维向量]` |
| 融合 | BM25 跨域查询 0 结果 | 多词查询要求全 token 命中，wiki 无 RAG 域词 | 用纯 wiki 域词触发 full fusion；降级 rag_only 是预期分支 |
| 问答 | `rag_limit=0` 崩溃 | ChromaDB 不接受 0 结果请求 | 纯形态直接调单路检索函数，不走融合入口 |

### 7.4 这套骨架能迁移到哪些业务

「稳定核心走编译 wiki + 易变长尾走向量 RAG + 路由 + 架构级融合」这套骨架，可以同构迁移到任何「知识有稳定层 + 易变层」的领域：

| 业务 | 稳定层（走 wiki） | 易变层（走 RAG） |
|------|------------------|------------------|
| 法律知识助手 | 法条 / 合同模板 | 判例 / 咨询记录 |
| 医疗知识库 | 诊疗指南 / 药品规格 | 病例 / 检验报告 |
| 电商运营 | 品类规则 / 政策 | 工单 / 评价 / 促销变更 |
| 企业 IT 支持 | 系统架构 / SOP | 报障工单 / 变更记录 |

迁移时主要改这几处：双源域（保证两源同域）、wiki 语料类型、RAG 文档类型、路由两源描述文案、embedding 模型（双源同步换）、RRF k 值（默认 60）。

### 7.5 最后一句诚实话

混合架构的所有价值，建立在「你真的同时有稳定知识和易变知识、且单源真的不够用」这个前提上。**先用单源跑通，确认不够，再上混合。** 上了之后也别期待它在每个指标上碾压单源——它给你的是跨界综合质量和来源可溯，代价是你要管好那个会判错的路由器。把这条边界守住，混合架构才是工具而不是负担。
