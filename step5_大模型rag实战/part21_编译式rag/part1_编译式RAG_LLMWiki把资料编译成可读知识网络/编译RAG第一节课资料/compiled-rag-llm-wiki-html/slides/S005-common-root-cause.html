共同边界：源材料变了，中间产物都要更新

传统 RAG 更新索引，编译式 RAG 更新 wiki——区别不在"谁自动同步"

传统向量 RAG
源文档：99 → 199
向量索引：仍是 99（旧快照）
查询：命中旧 chunk，答 99
必须 rebuild / 增量更新索引，新值才生效
vs
编译式 RAG
raw/：20 → 50
wiki/：仍是 20（旧产物）
查询：读旧 wiki 页，答 20
必须 re-ingest / compile，新值才生效
共同点：两者都依赖中间产物，中间产物不更新就用旧内容回答——"答旧值"不是传统 RAG 独有的毛病。
机器索引
chunks / embeddings / 向量索引——给机器读、高度优化的黑箱，人难直接打开审查
可读 wiki
markdown / index.md / log.md——给人读，可 diff、可审计、可 log，组织过程看得见
常见误区：以为"编译式把知识沉淀了，更新自然就跟上"——其实它同样不会自动同步，raw 改了不重新 ingest，wiki 还是旧产物。
→ 真正的分野不在"谁自动同步"，而在：我们想维护一个机器索引，还是一份可读、可治理的 wiki？
