# 编译式 RAG 的成本争议

## 核心争议

[[compiled-rag|编译式 RAG]] 的核心卖点是「**一次编译、长期复用 → 查询成本被摊薄 → 长期更省**」。一项**预注册对照实验**直接对这条卖点发起证伪：编译式 wiki 查询约 **165 万 token**，向量 RAG 仅约 **8 万 token**——**编译式查询成本约为向量 RAG 的 20 倍**。

> 预注册对照实验实测：编译式 ≈ 165 万 token vs 向量 RAG ≈ 8 万 token → ≈ 20×。
> ——见 frontmatter sources（preregistered-critique.md）

## 双方立场

**正方（[[compiled-rag|概念源头]]）**
- 摊薄视角：编译成本是**一次性**的，查询侧省下来的成本会在多次查询中摊销
- 资产视角：产物是**可审计、可版本化**的 wiki，不是临时拼接的 prompt 上下文
- 长期视角：wiki 是**复利资产**，复用面越广、越往后越省

**反方（预注册证伪）**
- 实测视角：在**单次查询**口径下，编译式读全文是 20× 成本
- 可证伪视角：用了**预注册**协议（事先固化假设与口径），避免事后凑数
- 摊薄假设的边界：如果查询频次不够高，摊薄根本发生不了

## 适用边界

| 场景 | 摊薄假设是否成立 | 倾向 |
|---|---|---|
| 高频、长期复用的内部知识库 | 摊薄窗口长、复用面大 | 编译式更划算 |
| 一次性 / 低频查询 | 摊薄几乎不发生 | 编译式 20× 劣势 |
| 需要可审计/可版本化的资产 | 复利属性强 | 编译式有额外价值（非纯成本） |
| 大语料 + 短答案 | 读全文浪费严重 | 向量 RAG 更省 |

## 未解问题

- "摊薄"的具体触发频次阈值是多少？预注册实验未给出
- 编译侧的 LLM 成本是否被纳入对比？如果计入，**总成本**口径下结论可能翻转
- 同一查询任务下，编译式产物页**真的**不需要二次精读吗？这取决于 [[gbrain|系统]] 的 Retrieval 实现
