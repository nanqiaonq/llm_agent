组件速查 · 把集群当成一家餐厅

把整个 k8s 集群类比成一家连锁餐厅 (多间分厨房), 16 个组件各司其职。点击图中任一组件可看完整介绍。
K8s 组件 关键作用 餐厅角色
━━━ 集群外 (餐厅外援) ━━━
kubectl开发者 / 运维跟集群说话的 CLI 工具老板的 iPad 后台
browser公网用户, 只认公开域名来吃饭的顾客
registry存所有镜像, kubelet 拉镜像找它食材冷库
━━━ 控制面 (餐厅总部) ━━━
api-server集群唯一入口, 唯一能动 etcd订单系统 (POS)
etcd所有资源状态的强一致数据库餐厅总账本
controller-mgr几十个 controller, 期望 vs 实际 reconcile厨房经理团队
scheduler给 pending pod 派工位 (筛选/打分/绑定)派单员
Service虚拟 IP, 给一组 pod 起稳定名字取餐窗口号(虚拟)
━━━ 工作面 (每间分厨房) ━━━
kubelet节点上唯一系统进程, 起容器 + 心跳工位主厨

所有 k8s 进程 (api/etcd/cm/sched/kubelet/proxy) 都不在顾客点菜的传菜路径上。真正"端菜"的是 Linux 内核 netfilter + CNI, k8s 组件只是"配置员"。

部署 / 调度

下发部署 14 步
演示完整的 Deployment 部署链路: 从开发者敲 kubectl apply 到所有 pod running, 14 步逐步播放。

核心组件

  • kubectl → api server → etcd → controller mgr → scheduler → 各节点 kubelet → containerd → registry

日志步骤要点

  • ① kubectl 发 HTTPS POST 到 api :6443, 携带 yaml 文本
  • ② api 完成 认证 / 鉴权 / 准入控制, 把 Deployment 写入 etcd
  • ③ Deployment Controller reconcile → 创建 ReplicaSet → 再创建 N 个 pending pod
  • ④ scheduler 三阶段调度: 过滤 Filter (剔不满足节点) → 打分 Score (多维评估) → 绑定 Bind (写 nodeName)
  • ⑤ 各节点 kubelet watch 到分配 → 通过 CRI 调 containerd 起容器
  • ⑥ containerd 向 registry 拉镜像 → 起 pod
支持「上一步 / 下一步 / 自动播放」步进控制, 配合 YAML 弹窗预览。
滚动升级 (v1→v2) 零中断
生产最常见操作: 改 image 版本后, k8s 用 maxSurge=1 / maxUnavailable=0 策略逐个替换 pod, 全程不中断业务。

核心机制

  • Deployment Controller 自动创建新 ReplicaSet (rs-v2), 旧 rs-v1 保留供回滚
  • 每轮: 起 1 个 v2 → 等 Ready 加入 EndpointSlice → 退 1 个 v1 (Service 立即摘除)
  • kubelet 给被退的 v1 pod 发 SIGTERM, 等 30s grace 优雅退出

日志要点

  • kubectl set image deployment/users-api api=users-api:v2.0 触发
  • 每轮分 A (起新) / B (退旧) 两阶段, 重复 N 次直至全部替换
  • 旧 ReplicaSet 保留 (revisionHistoryLimit=10), 出问题 kubectl rollout undo 一键回滚
这是真实工作里 90% 的发布场景, 比 HPA 更日常。

故障自愈

pod 宕机 本地自愈
单个 pod 在节点上异常退出 (OOMKilled / panic / liveness 失败), 由所在节点的 kubelet 本地原地重启容器, 不经过 cm/scheduler/跨节点。沙箱 (pause 容器) 保留 → Pod IP 不变。

核心机制

  • kubelet 通过 liveness/readiness probe 或容器退出事件检测到异常 → 本机 readiness 标 false
  • kubelet 上报 → cm EndpointSlice Controller 把该 endpoint 标 ready=false → 所有节点 kube-proxy 调 iptables 临时摘除该 endpoint, 新流量绕开
  • kubelet 按 pod.spec.restartPolicy=Always 在本节点原地重启容器 (沙箱保留, IP 不变, restartCount +1)
  • readiness 恢复 → cm 改回 ready=true → 各节点 kube-proxy 把 endpoint 加回 NAT 规则
  • 不涉及调度器, 比 节点宕机 快几个数量级
单 pod 故障恢复时间 ≈ 几秒, 节点故障要 5+ 分钟。
readiness probe 的真正价值: 容器还没准备好时, 整个集群通过 kube-proxy iptables 临时绕开它, 流量不打到正在重启的实例上。
节点宕机 跨节点重调度
整个 worker 节点失联 (电源/网络断), 该节点上的 pod 全部丢失, k8s 在其他健康节点上重建。

关键时间线

  • T+0: 节点断电, kubelet/proxy 的 watch 长连接 TCP 中断
  • T+40s: api 持有的 NodeLease 过期 → cm 的 node-controller 标 NotReady
  • T+5min: pod-eviction-timeout 触发 → 驱逐该节点上的 pod
  • ReplicaSet 发现 running < desired → 创建新 pending pod
  • scheduler 重新调度 (Filter 排除 NotReady 节点)
  • 健康节点 kubelet watch 到新 binding → 拉起替补 pod

对外部访问的影响

  • gateway controller (3 副本 + podAntiAffinity 散在 3 节点) 在该节点的副本也丢了
  • 但生产环境前面的云负载均衡 (本 demo 已省略) 通过 ~5s 健康检查会把故障节点剔除, 流量自动切到剩余 2 个 gateway → 外部用户无感知
k8s 自愈 ≠ 业务连续。真正保业务连续的是 多副本 + LB 健康检查 这两层。

流量演示

用户访问 外部 → 内部
外部用户 → 业务 pod 的完整数据路径, 两次内核 DNAT。这种"集群外 → 集群内"的流量, 业内俗称「南北向」(穿过集群边界)。

完整链路 (6 步)

  • ① 浏览器 → 公网 DNS 解析 example.com → 节点 IP → HTTPS 请求 (生产环境前面通常有云负载均衡, 本课 k3s 直接打节点 IP, 故省略 LB 节点)
  • ② 包到达 worker 节点的 NodePort (例如 10.0.0.1X:30443), 由节点内核接管
  • ③ 包到节点 → 内核 netfilter 第一次 DNAT: 节点 IP:30443 → gateway pod IP:443
  • ④ gateway 完成 TLS 终止, 按 HTTPRoute 转发到 Service ClusterIP 10.96.x.x:80
  • ⑤ 内核 netfilter 第二次 DNAT: ClusterIP → 真实 pod IP (kube-proxy 不在数据路径, 只写规则)
  • ⑥ 包经 CNI (Calico) 跨节点路由, 抵达目标 pod
所有 K8s 进程都不在数据路径上, 真正搬运字节的是 Linux 内核 + CNI。

自动伸缩

HPA 伸缩 扩容 + 缩容
HPA (HorizontalPodAutoscaler) 不是独立进程, 是 kube-controller-manager 内置的一个 controller。演示完整周期: 流量↑→扩容→稳定→流量↓→缩容。

扩容阶段

  • 已有 pod CPU 飙升 → 红色 CPU 仪表 (> 70% 阈值)
  • 各节点 kubelet 的 cAdvisor 上报指标 (简化: 直接到 cm; 实际经 metrics-server)
  • cm 里 HPA 计算: desired = ceil(N × cur% / target%)
  • PATCH Deployment.replicas → 走标准调度流程 → 新 pod 起来分担流量 → CPU 回落

缩容阶段

  • CPU 长时间低位 → HPA 决定缩容
  • 等 stabilizationWindow=300s 防抖 (此处加速)
  • PATCH replicas 下调 → kubelet SIGTERM + 30s grace 优雅终止
HPA 默认看 CPU/内存, 高级场景可用自定义指标 (Prometheus Adapter)。

控制操作

步进控制 · 上一步 / 下一步 / 自动播放 / 重置
仅在「下发部署」期间可用, 用于精细控制 14 步的播放节奏。
  • 下一步: 推进到下一阶段, 触发对应动画 + 日志
  • 上一步: 回滚到上一阶段 (基于状态快照, pod / 指标 / 日志全还原)
  • 自动播放: 每 2.2s 自动推进, 末尾自动停止
  • 重置: 清空 pod / 日志 / 指标, 回到初始态
